## Heap Manager Architecture

### Overview

The heap manager provides a clean, low-level API for Smalltalk object allocation and access, completely separated from high-level semantic knowledge. It uses tagged OOPs for SmallIntegers and ObjectTable indirection for heap objects.

### Core Components

#### ISmalltalkHeapManager Interface

```csharp

    ushort GetIndexedWord(SmalltalkOOP objectOOP, int index);             // Bitmaps
```

#### Tagged OOP System

```csharp
public readonly struct SmalltalkOOP
{
    private readonly int _value;
    
    public bool IsSmallInteger => (_value & 1) == 1;
    public bool IsObjectPointer => (_value & 1) == 0;
    
    public int AsSmallInteger() => _value >> 1;
    public int AsObjectTableIndex() => _value >> 1;
    public int RawValue => _value;
    
    public static SmalltalkOOP FromSmallInteger(int value) => new((value << 1) | 1);
    public static SmalltalkOOP FromObjectTableIndex(int index) => new(index << 1);
}
```

**Critical Principle**: Only tagged SmalltalkOOP values should be stored or passed between methods, never raw object indices (`int`). This prevents double-tagging bugs.

#### Object Format Enumeration

```csharp
public enum ObjectFormat : byte
{
    Pointer = 0,          // Fixed instance variables only
    PointerIndexed = 1,   // Instance variables + indexed OOPs (Arrays, CompiledMethods)
    ByteIndexed = 2,      // Instance variables + indexed bytes (Strings, ByteArrays)
    WordIndexed = 3,      // Instance variables + indexed words (Bitmaps)
}
```

### Key Architectural Benefits

1. **No Semantic Knowledge**: Heap manager doesn't know about classes, symbols, or special objects
2. **Type Safety**: Format-specific access methods prevent wrong data type access
3. **Bounds Checking**: All array accesses are validated against object bounds
4. **Tagged Pointers**: SmallIntegers stored directly in OOPs for efficiency
5. **Flexible GC Roots**: Cold start configures minimal fundamental roots

## Bootstrap Process

### Overview

The cold start bootstrap creates a complete Smalltalk object memory through a carefully orchestrated 15-phase process. Each phase has specific responsibilities and builds upon previous phases.

### Bootstrap Triangle

The bootstrap process must solve a fundamental circular dependency:

```
    Classes
   ╱        ╲
  ╱          ╲
Methods ──── Objects
```

- **Classes** define the structure of objects
- **Objects** are instances of classes  
- **Methods** are objects that belong to classes

**Solution**: The bootstrap process uses multi-pass initialization (Phases 6, X, Y) to resolve circular dependencies, then proceeds with full allocation+initialization (Phases 7-14).

## Init Expression Execution (Post-Cold Start)

After the 15 cold start phases complete, init expressions execute to initialize class variables, set up globals, and configure the runtime system. Each init expression is a pre-compiled DoIt that runs as an ordinary method activation.

### GC-Safe Allocation Order

**Critical Design**: Init expression execution must create both a Process and a MethodContext. Since either allocation could trigger AutoGC, we must ensure objects are rooted before subsequent allocations.

**The Problem**: If we create objects in the wrong order:
1. Create MethodContext (allocates on heap)
2. Create Process (allocates on heap) ← AutoGC might run here!
3. Wire Process.suspendedContext = MethodContext

If AutoGC runs during step 2, the MethodContext from step 1 is **NOT rooted** (only held in a C# local variable). GC collects it, and its OOP gets reused - potentially for the Process being created! This causes Process.suspendedContext to point to **itself** (circular reference), corrupting the process state.

**The Solution**: GC-safe allocation order ensures each object is rooted before the next allocation:

```csharp
// Step 1: Create Process with nil suspendedContext
// (GC during allocation is safe - the Process being created won't be collected)
SmalltalkOOP processOOP = CreateProcessWithNilContext(priority: 8);

// Step 2: Set Process as activeProcess - now it's rooted via ProcessorScheduler
// (SetInstanceVariable doesn't allocate, so no GC can run here)
_heapManager.SetInstanceVariable(schedulerOOP,
    VMConstants.PROCESSORSCHEDULER_ACTIVEPROCESS_INDEX, processOOP);

// Step 3: Create MethodContext
// (GC during allocation won't collect Process - it's rooted via ProcessorScheduler)
SmalltalkOOP methodContextOOP = CreateMethodContextForInitExpression(compiledMethodOOP, receiverOOP);

// Step 4: Wire Process.suspendedContext = methodContext
// (SetInstanceVariable doesn't allocate, so no GC can run here)
_heapManager.SetInstanceVariable(processOOP,
    VMConstants.PROCESS_SUSPENDEDCONTEXT_INDEX, methodContextOOP);

// Step 5: Execute
```

**Key Insight**: The Process is the **first/activeProcess** during init expression execution. Setting it as `ProcessorScheduler.activeProcess` provides a natural GC root through the existing Smalltalk object graph (SystemDictionary → Processor → activeProcess).

### Root Chain During Init Execution

```
SystemDictionary (GC root)
  └── Processor (ProcessorScheduler singleton)
       └── activeProcess (Process)
            └── suspendedContext (MethodContext)
                 └── method (CompiledMethod)
                 └── receiver (Smalltalk global)
                 └── indexed slots (temp frame, stack)
```

### CreateProcessWithNilContext Helper

```csharp
private SmalltalkOOP CreateProcessWithNilContext(int priority)
{
    // Process has 4 instance variables: nextLink, suspendedContext, priority, myList
    var processOOP = _heapManager.AllocateObject(ObjectFormat.Pointer, 4, indexedSize: 0);
    _heapManager.SetClassOOP(processOOP, processClassOOP);

    // Set instance variables - suspendedContext is nil, will be set later
    _heapManager.SetInstanceVariable(processOOP, PROCESS_NEXTLINK_INDEX, nil);
    _heapManager.SetInstanceVariable(processOOP, PROCESS_SUSPENDEDCONTEXT_INDEX, nil);  // ← nil!
    _heapManager.SetInstanceVariable(processOOP, PROCESS_PRIORITY_INDEX, SmallInteger(priority));
    _heapManager.SetInstanceVariable(processOOP, PROCESS_MYLIST_INDEX, nil);

    return processOOP;
}
```

### Why Not Use AddGCRoot?

An alternative approach is to explicitly add the MethodContext as a temporary GC root:

```csharp
// Alternative (NOT recommended):
SmalltalkOOP methodContextOOP = CreateMethodContext(...);
_heapManager.AddGCRoot(methodContextOOP);  // Temporary root
SmalltalkOOP processOOP = CreateProcess(...);  // Safe now
_heapManager.RemoveGCRoot(methodContextOOP);
```

**Why GC-safe allocation order is better:**
1. **Natural rooting**: Uses existing Smalltalk object graph rather than special C# machinery
2. **Blue Book compliance**: Follows how Smalltalk-80 actually works (activeProcess is always rooted)
3. **Simpler**: No need to manage temporary roots
4. **Safer**: Can't forget to remove temporary roots
5. **Semantic correctness**: The Process IS the activeProcess during execution

**Problem**: 201 unreachable objects due to literal handling double-tagging bug.

**Root Cause**: Code was mixing raw object table indices (`int`) with tagged OOP values (`SmalltalkOOP`).

**Solution**: Changed all literal handling to use `SmalltalkOOP[]` instead of `int[]`.

**Files Modified**:
- `Phase8_MethodInstallation.cs`: Changed `ResolveLiteralValueAsOOP()` to return `SmalltalkOOP`
- `Phase11_InitExecution.cs`: Changed `ResolveLiteralAsOOP()` to return `SmalltalkOOP`
- `SemanticAllocator.cs`: Changed `AllocateCompiledMethod()` from `int[]` to `SmalltalkOOP[]`

**Results**:
- ✅ 31,927 objects allocated, 31,927 reachable, **0 unreachable**
- ✅ All OOP values correctly tagged once
- ✅ Perfect garbage collection achieved

### 4. Dynamic Class Name Resolution (2025-01-15)

**Problem**: Class names displayed as "UnknownClass" due to hard-coded instance variable index.

**Solution**: Dynamic index lookup from coldstart.json metadata.

**Implementation** (Loader.cs:55-64):
```csharp
if (_heapManager is SmalltalkHeapManager concreteHeapManager)
{
    int nameFieldIndex = ClassHierarchyUtils.FindInstanceVariableIndex("Class", "name", _bundle);
    if (nameFieldIndex >= 0)
    {
        concreteHeapManager.SetClassNameFieldIndex(nameFieldIndex);
    }
}
```

**Results**:
- ✅ Class names display correctly: UndefinedObject, False, True, Array, etc.
- ✅ No hard-coded indices - robust to Smalltalk source code changes
- ✅ All indices determined from coldstart.json at runtime

---

### 5. NULL_CLASS Bug Elimination (2025-01-13)

**Problem**: Phase 7 was creating objects with `classOOP=0` (NULL_CLASS).

**Solution**: Implemented bulletproof dual AllocateArray API:
- **Legacy API**: `AllocateArray(string className, int count)` for early phases (0-6)
- **New API**: `AllocateArray(SmalltalkOOP classOOP, int count)` for later phases (7+)

**Results**:
- ✅ NULL_CLASS issue completely eliminated
- ✅ All objects now have proper class references
- ✅ Impossible to forget class reference setting in new API
