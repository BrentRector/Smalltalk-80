# Smalltalk-80 Build Guide

**Last Updated**: 2025-11-17

## Overview

The Smalltalk-80 project uses a clean, coherent build system with separate output directories and explicit build scripts for different scenarios.

## Build System Architecture

### Output Directories

Each project has its own independent `bin/` and `obj/` directories:

```
Smalltalk-80/
├── Smalltalk80.Compiler/
│   ├── bin/Debug/net9.0/
│   │   ├── Smalltalk80.Compiler.dll
│   │   ├── coldstart.json              # Generated by build-standard.ps1
│   │   └── coldstart_with_tests.json   # Generated by build-with-tests.ps1
│   └── obj/
├── Smalltalk80.Interpreter/
│   ├── bin/Debug/net9.0-windows/
│   │   └── Smalltalk80.Interpreter.exe
│   └── obj/
└── (other projects...)
```

**Key Points**:
- No shared bin directory
- Compiler outputs to `Smalltalk80.Compiler/bin/Debug/net9.0/`
- Interpreter outputs to `Smalltalk80.Interpreter/bin/Debug/net9.0-windows/`
- coldstart.json files live in the Compiler's output directory

## Build Scripts

### Standard Build: `build-standard.ps1`

Generates the standard Smalltalk-80 cold start bundle (no tests).

**Usage**:
```powershell
.\build-standard.ps1
```

**Output**:
- `Smalltalk80.Compiler/bin/Debug/net9.0/coldstart.json`
- ~235 classes, ~4624 methods
- 31 initialize expressions
- 234 comment expressions (skipped)

**To run**:
```powershell
cd Smalltalk80.Interpreter
dotnet run -- --coldstart ../Smalltalk80.Compiler/bin/Debug/net9.0/coldstart.json
```

### Test Build: `build-with-tests.ps1`

Generates cold start bundle **with** BlockContext test suite.

**Usage**:
```powershell
.\build-with-tests.ps1
```

**Output**:
- `Smalltalk80.Compiler/bin/Debug/net9.0/coldstart_with_tests.json`
- ~236 classes, ~4745 methods (121 more than standard)
- 31 initialize expressions
- 1 test expression (`BlockContextTest new testAllCombinations!`)
- 234 comment expressions (skipped)

**To run**:
```powershell
cd Smalltalk80.Interpreter
dotnet run -- --coldstart ../Smalltalk80.Compiler/bin/Debug/net9.0/coldstart_with_tests.json
```

**Expected Result**: `3503` (all 120 BlockContext tests passing)

## Workflows

### Standard Development

For normal interpreter development and testing:

```powershell
# 1. Build standard bundle
.\build-standard.ps1

# 2. Run interpreter
cd Smalltalk80.Interpreter
dotnet run -- --coldstart ../Smalltalk80.Compiler/bin/Debug/net9.0/coldstart.json
```

### BlockContext Testing

When working on block context, bytecode generation, or variable resolution:

```powershell
# 1. Build test bundle
.\build-with-tests.ps1

# 2. Run interpreter with tests
cd Smalltalk80.Interpreter
dotnet run -- --coldstart ../Smalltalk80.Compiler/bin/Debug/net9.0/coldstart_with_tests.json

# 3. Verify test result
# Look for: BlockContextTest new testAllCombinations! → 3503
```

### Quick Rebuild

If you only modify the Interpreter (not Compiler or source files):

```powershell
cd Smalltalk80.Interpreter
dotnet build
dotnet run --no-build -- --coldstart ../Smalltalk80.Compiler/bin/Debug/net9.0/coldstart.json
```

The `--no-build` flag prevents rebuilding and avoids triggering the Compiler build.

## Common Scenarios

### Scenario 1: First Time Setup

```powershell
# Clone repository
git clone <repo-url>
cd Smalltalk-80

# Build everything
dotnet build

# Generate standard bundle
.\build-standard.ps1

# Run
cd Smalltalk80.Interpreter
dotnet run -- --coldstart ../Smalltalk80.Compiler/bin/Debug/net9.0/coldstart.json
```

### Scenario 2: Compiler Changes

If you modify the Compiler, AST, or bytecode generation:

```powershell
# Rebuild compiler
dotnet build Smalltalk80.Compiler/Smalltalk80.Compiler.csproj

# Regenerate bundle (choose one)
.\build-standard.ps1          # Standard
.\build-with-tests.ps1        # With tests

# Test
cd Smalltalk80.Interpreter
dotnet run -- --coldstart ../Smalltalk80.Compiler/bin/Debug/net9.0/coldstart.json
```

### Scenario 3: Interpreter Changes

If you modify the VM, primitives, or runtime:

```powershell
# Just rebuild interpreter
cd Smalltalk80.Interpreter
dotnet build

# Run with existing bundle (no rebuild)
dotnet run --no-build -- --coldstart ../Smalltalk80.Compiler/bin/Debug/net9.0/coldstart.json
```

### Scenario 4: Source File Changes

If you modify Smalltalk-80.st or test files:

```powershell
# Regenerate bundle (choose one)
.\build-standard.ps1          # If you modified Smalltalk-80.st
.\build-with-tests.ps1        # If you modified test files

# Run
cd Smalltalk80.Interpreter
dotnet run -- --coldstart ../Smalltalk80.Compiler/bin/Debug/net9.0/coldstart.json
```

## Release Builds

Both build scripts support Release configuration:

```powershell
.\build-standard.ps1 -Configuration Release
.\build-with-tests.ps1 -Configuration Release
```

Output goes to `Smalltalk80.Compiler/bin/Release/net9.0/`

## Troubleshooting

### "coldstart.json not found"

**Problem**: Running Interpreter shows warning about missing coldstart.json

**Solution**: Run one of the build scripts:
```powershell
.\build-standard.ps1
```

### "Old bundle being loaded"

**Problem**: Interpreter loads old data despite regenerating bundle

**Solution**: Use `--no-build` to prevent automatic rebuild:
```powershell
cd Smalltalk80.Interpreter
dotnet run --no-build -- --coldstart ../Smalltalk80.Compiler/bin/Debug/net9.0/coldstart.json
```

### "Test not executing"

**Problem**: BlockContextTest doesn't run

**Checklist**:
1. Did you use `build-with-tests.ps1`? (Not `build-standard.ps1`)
2. Bundle shows 4745 methods? (Not 4624)
3. Bundle shows 281 init expressions? (Not 280)
4. Using correct file: `coldstart_with_tests.json`? (Not `coldstart.json`)

## Migration from Old Build System

**Before** (shared bin directory):
```
Smalltalk-80/bin/Debug/net9.0/coldstart.json  # Shared output
```

**After** (project-specific directories):
```
Smalltalk80.Compiler/bin/Debug/net9.0/coldstart.json  # Compiler output
Smalltalk80.Interpreter/bin/Debug/net9.0-windows/     # Interpreter output
```

**Key Changes**:
1. Removed `BaseOutputPath` from `Directory.Build.props`
2. Removed auto-generation from Compiler build
3. Added explicit build scripts
4. Each project uses its own bin/obj

## Design Rationale

### Why Remove Shared bin Directory?

**Problems with shared bin**:
- Compiler and Interpreter use different target frameworks (net9.0 vs net9.0-windows)
- Auto-generation overwrote manually created test bundles
- Difficult to maintain both standard and test bundles simultaneously
- Build order dependencies caused confusion

**Benefits of project-specific bin**:
- Clear separation of concerns
- Standard and test bundles can coexist
- No auto-generation surprises
- Explicit control over what gets built

### Why Explicit Build Scripts?

**Problems with auto-generation**:
- Compiler always regenerated standard bundle on every build
- Test bundles had to be created manually and would get overwritten
- Running Interpreter triggered Compiler build → overwrote test bundle
- No clear workflow for testing

**Benefits of explicit scripts**:
- Clear intent: "I want standard" vs "I want tests"
- Both bundles can exist simultaneously
- No surprise overwrites
- Self-documenting workflow
